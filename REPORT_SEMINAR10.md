# Отчёт: Семинар 10 — Concurrent Simulation Framework

## Задача
Внедрение возможностей параллельного исполнения (multithreading) в существующий Sequential-фреймворк симуляции с использованием механизмов `java.util.concurrent`, без изменения архитектуры предыдущих семинаров. В качестве основы реализации выбрана декомпозиция сетки по строкам (Domain Decomposition).

## Сравнение Sequential и Parallel

| Аспект | Sequential | Parallel |
|--------|-----------|---------|
| **Архитектура** | Один `SimulationController`, один цикл выполнения через ExplicitEulerStepper и стейт-машину. | Интеграция `ExecutorService`, пула `SimulationWorker`, и барьерная синхронизация границ через `BoundaryExchangeManager`. |
| **Оверхед (Overhead)** | Минимальный, прямой доступ к памяти и циклам. | Значительный из-за создания потоков, использования пула `FixedThreadPool`, барьера ожидания и обмена Halo-границ. |
| **Ускорение (Speedup)** | 1x (базовое время). | ~N-1x (Amdahl's law). Ускорение наступает только при значительной матрице, где обсчёт превосходит затраты на синхронизацию. |
| **Сложность ООП** | Относительно низкая: данные и поведение сгруппированы просто. | Существенно выше. Разделение Ownership между потоками, изоляция локальных массивов `Subdomain` для обхода состояний гонки (Race conditions). |
| **Безопасность Данных** | Не требует дополнительных проверок. | Критична. Метод `Field.getValue/setValue` не потокобезопасен (not thread-safe), поэтому воркеры вычисляют шаги в изолированных `localData` структурах. Ошибочный partitioning приведет к скрытым состояниям гонки с порчей данных. Глобальный write-back выполняется безопасно после барьера. |

## Особенности реализации
1. **Декомпозиция (Domain Decomposition)**: Сетка 2D делится горизонтальными полосами через `DomainDecomposer`. Каждая полоса (вместе с фиктивными внешними слоями "halo") изолирована в классе `Subdomain`.
2. **Отложенная модификация (Thread Safety)**: Каждый `SimulationWorker` работает только с защищенными локальными копиями данных, что исключает прямую запись в глобальный объект `Field` до тех пор, пока вся вычислительная работа всеми воркерами не будет завершена.
3. **Обмен границ**: `BoundaryExchangeManager` выполняет обмен граничных строк (`rowEnd` первого воркера копируется в `rowStart-1` второго).
4. **Бесшовная интеграция**: Механизм распараллеливания был интегрирован через внедрение кастомной анонимной `IStepperStrategy` в `ParallelSimulationController`, позволяя переиспользовать уже написанный конечный автомат `SimulationController`.

## Отрицательный Speedup и размер сетки
Из-за высоких накладных расходов (обмен потоками контекста, ожидание барьеров `invokeAll` и копирование массивов), на сетках маленького размера (например, 10x10) параллельное исполнение часто оказывается **медленнее** Sequential. Выигрыш в производительности начинает проявляться на объемных расчетах, где асимптотически доминирует вычислительная часть — например, сетки размером 500x500 и выше.
